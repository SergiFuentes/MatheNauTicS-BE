# Game Result Integrity — Design for F-01a, F-01b and F-04

**Status:** Staged implementation. The backend now has an authenticated session-start endpoint and ticket persistence, plus the F-04 payload-consistency hardening. `/games/finish` still accepts legacy client-generated tokens until the frontend is migrated; this is not yet an enforcement boundary and must not be treated as a complete F-01 remediation. Nothing has been deployed.

The implementation in this PR rejects reuse of an existing `sessionToken` with a different user or changed result payload. It does not prevent a client from fabricating a result with a new token.
**Scope:** `POST /api/v1/games/finish`, the frontend completion call sites, and persisted game-session rewards.

## 1. Current behavior

The frontend submits `gameMode`, `score`, `coinsEarned`, `durationSeconds`, and a client-generated `sessionToken`. The backend:
- validates non-negative values and upper bounds (`score <= 1,000,000`, `coinsEarned <= 10,000` per session, `durationSeconds <= 3,600`);
- accepts only `adventure` and `training` game modes;
- persists the supplied score and reward values;
- uses a unique database constraint on `session_token` and returns the existing session for a repeated token.

This prevents out-of-range values and duplicate inserts for a reused token. It does **not** establish that the client-earned score or coins are legitimate. A modified client can submit plausible values with a new UUID. A UUID generated by the client is an idempotency key, not proof of a valid game.

## 2. Security goals

1. The server, not the client, determines the score and coins credited to a user.
2. Retrying one logical completion is safe and produces at most one persisted result/reward.
3. Reusing an idempotency key with a different payload is rejected rather than silently treated as the same completion.
4. Expired, unknown, cross-user, or already-finalized sessions cannot create additional rewards.
5. The migration remains compatible with existing stored sessions and does not change the meaning of `game_sessions.total_coins`: it stores the per-session reward; the balance is calculated by summing rows.

## 3. Recommended target protocol

### 3.1 Server-issued game sessions

An authenticated `POST /api/v1/games/start` operation now creates a server-side ticket in `game_session_tickets` containing:
- an unpredictable session identifier;
- the authenticated user ID and game mode;
- creation/expiry timestamps and a status (`ACTIVE`, `COMPLETED`, `EXPIRED`);
- a rules/version identifier for deterministic validation.

The response returns `sessionToken`, `gameMode`, and `expiresAt`. The current additive stage does not yet require `/games/finish` to use this ticket; that enforcement must follow after the frontend calls `/games/start`. The table currently records the ticket lifecycle metadata but does not yet derive scores or rewards.

### 3.2 Server-derived rewards

The server must derive credited values from evidence it can validate, rather than accept final totals from the request.

- **Training:** prefer server-issued multiplication challenges and submitted answers. The backend verifies challenge identity, answer correctness, ordering/reuse rules, and the reward for each accepted answer. The completion endpoint derives the final score/reward from accepted events.
- **Adventure:** the current runner score and coins depend on client-side gameplay state (including collected items and defeated enemies). A session nonce or signed start token alone cannot prove those events occurred. High-assurance validation requires a server-verifiable event protocol and deterministic validation/simulation of the relevant game rules. If full server simulation is out of scope, the residual trust in adventure results must be explicitly accepted; do not claim F-01a/F-01b fully remediated.

Do not simply move the existing `score` and `coinsEarned` fields into a new endpoint: that would preserve the trust problem.

### 3.3 Idempotent completion

The server should enforce completion atomically in the database. The first valid completion changes the session from `ACTIVE` to `COMPLETED` and stores the derived result. A retry of the same session returns the original result without crediting anything again. A completion request that reuses the same identifier but changes its semantic payload must return a conflict and must not mutate the stored result.

The implementation must handle concurrent completion requests with a database transaction and constraints/conditional update, not a process-local check alone.

## 4. Migration and compatibility

1. Inventory all frontend completion call sites and preserve one stable identifier across retries. Current frontend `main` already creates and passes a stable token in `PauseScene._saveGameOnQuit`; keep regression coverage for that behavior.
2. Add the server-side session lifecycle and validation contract before removing the existing final-total contract.
3. Deploy the backend contract and frontend caller changes in a coordinated, backward-compatible sequence. Do not silently accept both trusted and untrusted completion payloads indefinitely.
4. Preserve historical rows and the current per-session coin aggregation. Any schema change must be additive and have a Flyway rollback/forward-recovery plan.
5. Do not run fabricated-result tests against production accounts or award real production currency during verification.

## 5. Required tests

- A result outside existing numeric bounds is rejected before persistence.
- An unknown, expired, completed, or other user's session cannot credit a result.
- Correct and incorrect training answers produce only server-derived rewards.
- Repeated completion with the same session returns the original result and credits no additional coins.
- Concurrent completion requests for one session produce one result/reward.
- Reusing an idempotency/session identifier with a changed payload returns a conflict.
- Client-supplied `score` or `coinsEarned` cannot override server-derived values.
- Existing authentication, guest conversion, leaderboard, progress, and historical coin-balance tests continue to pass.

## 6. Rollout gates

- [ ] Agree the exact scoring/reward rules for each game mode and which adventure integrity level is required.
- [ ] Implement the session lifecycle and persistence with focused tests.
- [ ] Update the frontend call sites and retry behavior in a separate, coordinated PR.
- [ ] Run CI and a staging end-to-end test using disposable test users.
- [ ] Verify production migration state and deploy only after CI/staging pass.
- [ ] Update the remediation report only to the status supported by test evidence.

## 7. Explicit non-goals

- No change to score/reward limits in this design.
- No claim that a client-generated UUID prevents result fabrication.
- No framework/dependency upgrade bundled with gameplay-integrity work.
- No production deployment or database mutation from this design PR.

## 8. Related findings

- **F-01a:** client-controlled score — bounds remain, but plausible fabricated values are still possible.
- **F-01b:** client-controlled coins — bounds remain, but plausible fabricated rewards are still possible.
- **F-04:** replay/idempotency — this PR enforces payload consistency for a reused token and introduces server-issued tickets, but finish does not yet require those tickets. The enforcement rollout remains pending.
